IAviso Seguro uses SQLite for all structured persistence and a local versioned JSON corpus for RAG-based evidence retrieval. Neither component requires an external service, a vector database, or a managed cloud store — everything runs from the file system, which keeps the stack self-contained and easy to reproduce in development, CI, and Docker environments.

<Tip>
  Do not commit your SQLite database file to version control. It contains triage proposals, reviews, and audit events that may include sensitive workplace descriptions. Add `data/local/` to your `.gitignore` (it is already excluded in the reference repository). This database is intended for prototype use only; do not use it to store production or real-incident data.
</Tip>

## SQLite Database

IAviso Seguro creates and manages its own schema at startup. You only need to point `DATABASE_PATH` at a writable location.

<ParamField body="DATABASE_PATH" type="path" default="data/local/iaviso.db">
  File-system path to the SQLite database file. The parent directory must exist before the application starts. In Docker deployments, map `data/local/` to a named volume so the database survives container restarts.
</ParamField>

### What Is Stored

The database holds every artifact produced during a triage run:

| Table | Contents |
|---|---|
| **Notices** | The original hazard description, provider, model, sampling parameters, and the LLM-generated proposal (category, urgency, summary, department). |
| **Triage runs** | Per-execution telemetry: attempts, repairs, token usage, latency, cost, evidence fragments used. |
| **Reviews** | Human decisions (`approved`, `modified`, or `rejected`) with reviewer identity, optional comment, field corrections, and version. |
| **Comparisons** | Side-by-side results from concurrent `local` + `external` runs against the same input, written in a single atomic write once both providers have responded. |
| **Comparison reviews** | The single human classification recorded against a comparison, with per-field agreement counts computed at query time. |
| **Audit events** | Immutable timeline entries for each notice: reception, proposal, state transition, actor, and any field corrections. |

### Proposal Lifecycle and Optimistic Concurrency

All new proposals enter the system as `pending_review` with `version=0`. When a reviewer submits a decision, the request must include the `expected_version` of the notice it intends to act on.

```json
{
  "decision": "approved",
  "reviewer": "Ana García",
  "comment": "Clasificación correcta.",
  "expected_version": 0
}
```

If another review has already been committed (i.e. the stored version no longer matches `expected_version`), the API returns **HTTP 409** and the caller's decision is discarded without overwriting the winning record. This prevents duplicate or concurrent reviews from silently replacing each other.

The three possible decisions have the following semantics:

- **`approved`** — confirms the LLM proposal as the final classification.
- **`modified`** — accepted with corrections; requires at least one change to category, urgency, or department.
- **`rejected`** — dismisses the proposal; no final accepted classification is created.

### Docker Volume

When running with Docker Compose, the database path resolves inside the container. Mount the parent directory as a named volume so data persists across rebuilds:

```yaml
volumes:
  - ./data/local:/app/data/local
```

The example `docker compose up --build` in the README uses this pattern. The `.env` `DATABASE_PATH` value does not need to change — the container working directory maps the same relative path.

## Knowledge Base (RAG Corpus)

The prevention corpus is a local versioned JSON file. It is loaded at startup and queried on every triage run to supply evidence fragments to the LLM prompt. No vector database, embedding model, or external retrieval service is required.

<ParamField body="KNOWLEDGE_BASE_PATH" type="path" default="data/knowledge/prevention_docs.v1.json">
  File-system path to the versioned JSON corpus. Must exist and satisfy the corpus schema contract. If the file is missing or violates the contract, the API returns the stable error code `invalid_knowledge_base` (HTTP 500) and triage does not continue — the system will not attempt to classify a hazard with incomplete or unverified evidence.
</ParamField>

<ParamField body="RAG_MAX_SOURCES" type="integer" default="2">
  Number of document fragments to retrieve per triage run. Accepted range: `1`–`5`. After the tool call validates a closed-domain category, the retriever discards documents from other categories, then ranks the remainder by weighted lexical match. Ranking is deterministic; source identifier is used to break ties. The retrieved fragments are included in the LLM observation alongside the matrix rule.
</ParamField>

### How Retrieval Works

The triage pipeline runs in this order:

<Steps>
  <Step title="Initial categorisation">
    The LLM calls `consultar_matriz_riesgos` with a closed-domain category. The tool validates the category and returns the matching risk-matrix rule.
  </Step>
  <Step title="Corpus filtering">
    The retriever discards all documents whose category does not match, then ranks the remaining documents by weighted lexical overlap with the original hazard description.
  </Step>
  <Step title="Fragment selection">
    The top `RAG_MAX_SOURCES` fragments are selected. Ranking is deterministic; source identifier breaks any ties.
  </Step>
  <Step title="LLM observation">
    The selected matrix rule and fragments are assembled into the structured observation sent to the LLM for final proposal generation. The LLM response schema does not allow the model to declare its own sources — `ExecutionMetrics.evidence` is constructed by the backend from the retrieved fragments and persisted with each run.
  </Step>
</Steps>

This separation prevents a crafted hazard description from forcing a different category, inventing a reference, or causing a source that was not consulted to appear in the evidence list.

### Corpus Contract

The included corpus (`prevention_docs.v1.json`) is synthetic and didactic — it is not normative and does not replace professional PRL documentation. Each document in the corpus carries an identifier, title, section, version, and extract. These fields are displayed in the React SPA under **Evidencia consultada** for every triage result.

If you need to update or replace the corpus, ensure the new file satisfies the same schema contract; otherwise startup retrieval checks will raise `invalid_knowledge_base` before any triage request is processed.
